> 结论：整体口径没问题，可以直接用。下面是技术细节的修正和补充，供 【规则维护者】 合进 v2。权重和分数线不在我审核范围，仍待 【用户】 确认。
> 以下组件名和判断信号是 Java 后端行业通用知识，不是原文内容；原文条件本身我没有改。

## 一、需要改的地方

1. **H2 组件名排序**：原文技术栈是 Spring Boot 2.2 + Spring Cloud + Nacos，这一代最常见的是 **Sentinel**（和 Nacos 同属 Spring Cloud Alibaba），其次 Hystrix（已停止维护，老项目常见），Resilience4j 较少。建议写成「Sentinel / Hystrix / Resilience4j」。另补 Feign 超时的常见写法：`feign.client.config`、`ribbon.ReadTimeout / ConnectTimeout`、`fallback / fallbackFactory`。
2. **H3 不要把 RabbitMQ 和 RocketMQ 混为一类证据**：RocketMQ 自带「事务消息」，RabbitMQ 没有，用 RabbitMQ 做可靠消息一般是「本地消息表 + publisher confirm + 重试 + 消费端幂等」。【公司】 用的是 RabbitMQ，所以简历里出现「本地消息表 / outbox / 发件箱」比出现「RocketMQ 事务消息」更对口。Seata（AT/TCC）也算 H3 相关，但它是分布式事务方案，不等于「异步 + 补偿」，只写 Seata 按「提及」处理，面试追问。
3. **「提及」档对 H1、H3、H5 太宽**：这三条是「做过什么」的经历要求，不是技能。只在技能栏写「熟悉分布式事务 / 微服务」不能算提及，建议这三条的技能栏关键词记 0 分，项目里一句带过才算「提及」。H2、H4 是技能类，保留现在的口径。这样能挡住关键词堆砌的简历拿到 37 分左右的硬性分。
4. **H4 证据补充**：CI 按改动路径构建，在 GitLab 里通常是 `rules: changes` 配合 Maven `-pl xxx -am`；版本统一常见 `dependencyManagement / BOM`、`${revision}` + flatten-maven-plugin、maven-enforcer-plugin（依赖收敛）。仓库合并保留历史常见 `git subtree` / `git filter-repo`。写到这一层的基本是真做过。Jenkins 也算，但 GitLab CI 更对口。

## 二、「真做过 vs 只会说」技术信号（补第二节）

| 项 | 真做过的信号 | 只会说的信号 |
|---|---|---|
| H1 | 写了拆的顺序和过渡方式：双写、灰度开关、按门店/商户灰度、绞杀者式逐步替换；写了一次回滚或事故 | 「主导微服务架构升级」+「系统性能提升 X 倍」，没有过渡方案、没有回滚 |
| H2 | 写了具体问题：雪崩、线程池打满、超时重试导致重复下单，以及怎么改的 | 技能栏「精通 Spring Cloud 全家桶」，项目里只列组件名 |
| H3 | 说得出「先写库还是先发消息」「消息发失败 / 重复消费怎么办」，提到幂等键、死信队列、对账任务修数据 | 2PC、TCC、Saga、最终一致性全部列上，但没说自己用了哪一种、为什么 |
| H4 | 有数字：几个仓库 / 模块合成几个、构建时间从多少降到多少、怎么处理依赖冲突 | 「负责 DevOps 体系建设」，没有 Maven 层面的动作 |
| H5 | 具体到代码：「把 5000 行的 OrderService 拆成…」、补了单测、有 GitHub/GitLab 链接 | 动词全是「负责 / 主导 / 规划 / 评审」，近两年没有任何编码描述 |

通用提醒：「QPS 提升 300%」这类数字很容易写，单独出现不算证据；要和具体做法连在一起才算「实证」。

## 三、追问题库补充（区分度更高的问法）

| 编号 | 追问 | 想听到什么 |
|---|---|---|
| H1 | 下单服务拆出去后，支付回调比订单落库先到，你们怎么处理？ | 状态机、重试或延迟消息、对账兜底，而不是「不会发生」 |
| H2 | Feign 超时后自动重试，下游其实已经扣款成功了，怎么办？ | 关掉非幂等接口的重试、幂等键、查询补偿 |
| H3 | 先写库再发 MQ，发消息失败怎么办？发成功了但本地事务回滚了又怎么办？ | 本地消息表 / outbox + 定时补发 + 消费端幂等 |
| H4 | 14 个仓库合成一个，git 历史怎么保留？各仓库同一个依赖版本不一致怎么收敛？ | subtree / filter-repo、BOM、enforcer、分批合并 |
| B2 | fastjson 漏洞你们具体升到哪个版本，或者换成了什么？怎么确认没有漏掉的调用点？ | 开 safeMode 或关 autoType、升级到 fastjson2 或换 Jackson、全局扫描调用点 |

## 四、我不改的
- 淘汰项 X1–X4、目标公司分档、输出格式：没有技术问题。
- 年限、学历、带人是否必须、对外岗位名称：不是技术口径，按 【规则维护者】 已列的待核实走。

## 五、技术能力评价要点（2026-11-03 应 【用户】 要求，供评分表 v4 用）

技术能力内部按 100 分打，再按 【用户】 定的权重折算。每项分三档：实证（具体项目、本人动作、结果）给满分，提及给一半，找不到给 0。

| # | 要点 | 分 | 实证看什么 | 只算提及的情况 |
|---|---|---|---|---|
| 1 | 存量系统渐进改造 | 30 | 在跑着的交易系统上逐步拆分或重构，写了过渡方式（灰度、双写、切流）和回滚 | 从零新建的微服务；整体重写（即使有灰度切流） |
| 2 | 交易一致性 | 25 | 本地事务调远程造成的脏数据怎么修；本地消息表/outbox 或事务消息、补偿、幂等、对账 | 只列 TCC/Saga/最终一致等名词 |
| 3 | 服务治理与稳定性 | 20 | Feign/RPC 超时、熔断、降级（Sentinel/Hystrix 等）的具体配置或事故复盘；fastjson 等安全漏洞治理 | 只写"精通 Spring Cloud"；用 Dubbo 做过同等治理的也按提及 |
| 4 | 亲自编码 | 15 | 近两年仍写代码：拆大类、重构模块、开源项目或提交记录 | 动词全是负责、主导、规划 |
| 5 | 工程治理 | 10 | 多仓库合并、Maven 多模块、父 POM/BOM、CI 按路径构建 | 只写 Jenkins/DevOps；没写不判淘汰，面试核实 |

技术栈吻合度（Java 8、Spring Boot 2.x、Nacos、RabbitMQ、MyBatis-Plus、GitLab）不单独打分，同分时优先。

### 折算到 v4 技术能力 50 分
存量系统渐进改造 15（实证 15 / 提及 7 / 无 0）、交易一致性 12（12/6/0）、服务治理与稳定性 10（10/5/0）、亲自编码 8（8/4/0）、工程治理 5（5/2/0，简历没写不进淘汰规则，面试核实）。
改造、一致性、亲自编码三项只在技能栏出现记 0；服务治理、工程治理在技能栏出现算提及。
不合适规则建议：改造和一致性两项都为 0 判不合适；工程治理为 0 不计入。
